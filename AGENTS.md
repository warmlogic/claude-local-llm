# AGENTS.md — local-llm developer guide

This is the canonical contributor guide, at the repo root. `.claude/CLAUDE.md` is a symlink to this file, so Claude Code loads the same content as project memory.

Claude Code plugin that runs two small MCP servers backed by a model running locally in LM Studio: houtini-lm (pinned) for text jobs on files, and local-verify (ours, node stdlib) whose `verify_claims` tool asks the model whether claims follow from a file. Text in, text out, inference over loopback only, fenced read-only file access. The main session calls the plugin's tools directly, guided by delegate-local and the explicit-only batch-local skill.

## Running tests

```bash
bash tests/test-fence.sh   # must pass before committing; includes test-context-cap.mjs
node --test tests/test-context-cap.mjs  # offline context, hint and batch bounds
```

Tests drive `scripts/launch-server.sh` and `scripts/launch-verify.sh` over stdio MCP JSON-RPC (`tests/mcp-call.mjs`, node stdlib; `tests/fake-endpoint.mjs` is a loopback stand-in for LM Studio) using `mktemp` roots and generated synthetic fixtures. Needs `node`, `jq`, `curl`. Cases that need a model (happy path, oversized input) print `SKIP` when LM Studio is unreachable at `LOCAL_LLM_ENDPOINT_URL` (default `http://127.0.0.1:1234`); every fence case, the 1 MB cap and endpoint passthrough run without one. The oversized case assumes LM Studio loads the model at a 32k context and fails, not skips, if a 130k-char file is accepted. Scratch dirs under `tests/.tmp-*` are gitignored and removed on exit. `test-fence.sh` also runs `tests/test-verify.sh`, the local-verify suite, which never needs a model: every answer comes from `fake-endpoint.mjs` in a `verify*` mode. It also runs `tests/test-batch.sh`, the batch-runner suite, likewise offline against `fake-endpoint.mjs` in a `batch*` mode.

`node tests/eval-verify.mjs [k]` is the verifier's live eval and is **not** per-commit: it sends the jev spike's two 48-item synthetic sets (`tests/fixtures/verify/`) through the launcher and tool on the loaded model (about 4 minutes), prints a table beside the spike's numbers, and exits non-zero on any unanimous false accept of a lookup claim, or on any failed or partial call. Each item declares its kind as the tool description tells Claude to (24 easy items are lookup; every hard item is computed). `EVAL_OUT=<file>` keeps one JSON line per item. Measured at k=10 on `qwen3.6-35b-a3b-splash`: easy 48/48 with 0 false accepts, lookup 24/24 (spike 48/48, 0); hard 34/48 with 12 false accepts, 2 of them unanimous (spike 33/48, 15, 7), the same across three runs since the seeds are fixed.

`tests/test-delegation.sh` is the delegation acceptance harness and is **not** part of the per-commit suite: every run is a real `claude -p` session and costs quota (a default run is 55 sessions: five each of a, a2, b, c, d, g, h, j and l, and ten for e's two turns, plus a few cheap judge calls). It loads temporary plugin copies with `--plugin-dir` (each sets its own `allowed_dirs` default, since the manifest has none: the fixtures folder, or the project in h and j), passes no `--allowedTools`, scores the stream-json traces with jq (tool uses joined to their results by `tool_use_id`), and treats an unparseable trace, a missing result event or a non-zero `claude` exit as a failed run. `DELEG_SELFTEST=1 DELEG_JUDGE=stub bash tests/test-delegation.sh` scores the hand-written traces in `tests/fixtures/deleg/` offline, and `test-fence.sh` runs that self-test on every commit (every assertion must pass, the printed total must equal the number of `expect*` lines, and a missing or unsummarizable fixture is an error, never a pass). Re-run the harness after editing `skills/delegate-local/SKILL.md` when paid sessions are authorized; otherwise run its offline self-test.

The default is now off, so `run_claude` explicitly exports `CLAUDE_PLUGIN_OPTION_DELEGATE_TASKS=classify,extract` for the harness sessions unless the caller already supplied that variable (including an empty value). This enables the hint for unprompted cases **a, a2 and h**, and keeps the outage and negative controls exercising the opted-in path. `--plugin-dir` loads the temporary plugin copies; the child process inherits this environment override, which the size hook reads before the manifest default. No user settings are saved or changed. The offline self-test stubs the launcher command to check the opt-in and preservation of explicit values; `test-context-cap.mjs` and `test-fence.sh` separately check a silent default hint for a 35k file and the retained above-cap warning.

Cases (a case passes at 4 of 5):

- **a**: a 35k-char file with the prompt "Classify <path> in five bullet points." is delegated unprompted (`code_task_files` succeeds on it; the footer houtini writes, the last `Model:` line of the result, must show a complete read equal to the number of paths and none of the bad-answer flags listed in the skill's names table, which is the only place the harness reads them from) and little of the file reaches Claude: exposure at most 0.10.
- **a2**: the same as a for a 35k-char prose document with a neutral name (`notes-0412.md`) and the prompt "Classify this document: <path>", which never names the tool or the size (real files do not carry `35k` in their names).
- **g**: the prompt "Use the local model to classify <path>" on that document: delegated as in a, and no plugin permission denial.
- **h**: a real-looking project, since the path decided the outcome on real files: a git-initialized `acme-billing/` (README.md, `src/`, and a 35k-char prose `docs/architecture-decisions.md`) under the harness's temp root, with no `tests/`, `.tmp` or plugin name in any path segment the model sees. The session cwd is the project, the plugin copy's `allowed_dirs` default is the project (rewritten the way `endpoint_url` is), and the prompt is "Classify <path> in 5 bullets.". Delegated as in a.
- **j**: the same doc with a judgment prompt, "Is the decision in <path> the right call? Argue it.". Not delegated: no `code_task_files` call and Claude reads the file itself (as b). It guards against a hint so strong that judgment work goes to the local model.
- **b**: a 2k-char file is read directly: no `code_task_files` call, exposure at least 0.5.
- **c**: endpoint down: the tool fails with `fetch failed`, is not called again, and Claude reads the file itself (exposure at least 0.5).
- **d**: endpoint up with no model loaded (`fake-endpoint.mjs no-model`): the same, with `No models loaded`.
- **e**: one session, two turns (`--resume`), endpoint down. Turn 1 is as c and its final reply must tell the user about the outage with a cause and a way to retry; in turn 2 Claude reads the second file, makes no `code_task_files` call, and no assistant text block mentions the outage.
- **l**: one 35k log and a single-file extraction prompt; no batch runner launch. Included in the default case list.
- **f**: no `permission_denials` entry names the skill call or a plugin tool in any inspectable trace, including batch Bash commands. Other denials print as "other denials (not plugin)" and do not gate: with default permissions Claude's own compound shell commands can still prompt, as in any session.

**Exposure** answers "did the file's content reach Claude's context?" without listing read commands. Every line of a fixture carries two unique markers, its first and its last field (the log timestamp and an `eol=` id); a line counts as exposed when either appears in the text of any tool result, so `cut -f2-` does not hide it. Exposure is the fraction of the file's lines exposed, and the limit is that a reader which removes both markers evades the metric. The text of all tool results counts, the local model's answers included (an answer that echoes the file is the file reaching Claude). The two logs in case e use distinct token namespaces, so re-reading the first file cannot satisfy turn 2. The generated fixtures consist of whole lines, sized at or just under their target, so no marker is a fragment. Any tool or shell form that reads the file counts, and a narrow search for a pattern (a few lines) stays near 0. On the saved traces, delegated runs measured 0 to 0.09 and full reads measured 1.0, which is why the thresholds are 0.10 and 0.5.

**Judge.** Whether text mentions the outage is decided by one `claude -p --model haiku` call with tools off and a JSON schema (`mentions_local_model_unavailable`, `gives_cause`, `gives_retry`; the verdict is in the result event's `.structured_output`), cached by text. `DELEG_JUDGE_CHECK=1 bash tests/test-delegation.sh` scores it against 24 labeled messages in `tests/fixtures/deleg/judge-labels.json` (the phrasings reviewers raised plus log sentences that must not count) and needs at least 23; the current prompt scored 24/24 in four of five checks and 23/24 in the fifth. `DELEG_JUDGE=stub` swaps in canned verdicts from `judge.json` for the offline suite.

Knobs: `DELEG_RUNS` (5), `DELEG_CASES` ("a a2 b c d e g h j l"), `DELEG_MODEL`, `DELEG_OUT` (trace dir, kept), `DELEG_ALLOWED_TOOLS` (passed to `--allowedTools`; setting it voids the no-prompt result, since it grants the permissions under test), `DELEG_SETTING_SOURCES` (default `project`, which keeps the user's own settings, allow rules and hooks out; hooks are not disabled because the plugin's own hook approves the skill call). Case k and its ticket/trace fixtures were removed: unprompted batch routing is no longer a goal. Cases a, a2, b, g, h, j and l need LM Studio to list a model at `127.0.0.1:1234`; a skipped case makes the run exit non-zero. Needs `claude`, `jq`, `node`, `curl`, `shasum` and `timeout` (or `gtimeout`).

Historical measurements with summary prompts, before the default narrowed to classification and extraction (not rerun for the revised prompts): a 4/5, a2 5/5, b 5/5, c 5/5, d 5/5, e 5/5, g 3/5, h 4/5, j 5/5, f 0 plugin denials in all 50 inspectable traces of a full pass. The a and h misses read a few more than the spot-check lines (exposure 0.16 and 0.14). The g misses are local-model answers that ran to the token limit (a `Quality:` flag) on the repetitive synthetic prose, which the skill correctly discarded in favor of reading the file; g is the noisy case (this change: 3/5, 3/5, 8/10 over three runs; the previous commit: 4/5, 6/10), so judge it over more than five runs. On the whole-line fixtures, the share of the file quoted back by the 9 delegated a2 and g answers was 0 in 8 and 0.01 in 1; earlier runs on fixtures whose last line was cut showed one runaway answer at 0.09. The outage path says to read the whole file with `Read`; without that, the spot-check rule for delegated answers made fallback reads sample the file and e dropped to 1/5 to 3/5 across runs. Within a single turn the model reliably writes an outage note at the failure and recaps it in the final reply, and no wording suppressed that, which is why e spans two turns.

## Measuring

`bash measure/run.sh` is the one command that reproduces `docs/results.md`, the definition-of-done numbers (Claude cost per job, usable answers, fixed cost, break-even, per-size savings, with the token sum and context growth beside them). A run's table is `<run-dir>/results.md`; `docs/results.md` is the hand-written summary of the findings, and a full run replaces it only with `MEASURE_PUBLISH=1`, so fold new numbers in by hand. Every step is a real `claude -p` session and spends quota; a full run is 46 job and control sessions plus up to 26 judge calls. Run it while nothing else uses LM Studio, because shared use skews the local model's timing. `bash measure/run.sh --resume <run-dir>` continues a run that stopped: it keeps every run that has a `facts/<name>.json` (delete one to redo it), and a verdict counts only for the answer it graded, so a redone run is judged again. `bash measure/run.sh --report <run-dir>` re-renders a stored run without new sessions, applying the operator's review verdicts. `measure/selftest.sh` runs offline (synthetic traces and runs, a fake `$HOME` for the corpus rule, a fake judge), and `test-fence.sh` runs it on every commit.

- **Corpus.** `measure/select-corpus.sh` picks the newest matching files under `$HOME/github` and `$HOME/catalyst` by a fixed rule. It takes UTF-8 text files only, and skips symlinks, dot-dirs, build and vendor dirs, secret-looking names, and this project's own repo and planning dir. The content guard is conservative on purpose and excludes a borderline file. It drops any file with a known key shape, a credential keyword next to a value in any case or serialization (`Authorization: Bearer …`, `"token": "…"`, `password = …`, cookies, sessions, client secrets), or a bare Bearer or Basic credential. `measure/entropy.mjs` then drops any file holding a run of 32+ characters from `[A-Za-z0-9+/_=-]` above 4.0 bits per character of entropy. A pure-hex token tops out at exactly 4.0 bits, so a bare hex key is out of this guard's reach; only the keyword patterns can catch it. URL userinfo with a password and credential arguments (`--user u:p`, `-u u:p`, `--password x`, mysql-style `-p<value>`) are dropped too. On this machine that guard dropped about three in five candidates, logs above all; a short corpus beats a leak. The filter is best-effort defense-in-depth that errs toward dropping files, not a guarantee: the requirement is that the corpus is processed locally and no content or path is committed, and the baseline sessions read these files by design. It returns 10 main files of 20k–50k characters (`wc -m`; 3 logs, 3 transcripts and 4 docs where they exist, the shortfall filled by the newest leftovers) and one each near 2k, 5k and 10k characters. A missing root, an unreadable folder or file, and a failed secret scan are counted in warnings that never name a file; a filter that errors stops the selection rather than letting a file through. The first run freezes the manifest at `$MEASURE_HOME/corpus.tsv` with the corpus rule's fingerprint (`select-corpus.sh` and `entropy.mjs`); later runs reuse it and refuse it once either changes. A manifest short of 10 main files or a small slot stops the run before anything is spent: `MEASURE_RESELECT=1` picks again, and `MEASURE_ALLOW_SHORT=1` runs anyway with a private, incomplete report.
- **Privacy.** Paths, traces, answers, the graded file copies, judge prompts and the review sheet stay under `$MEASURE_HOME` (default `$HOME/.cache/local-llm-measure`, which must sit outside the allowed folders). `docs/results.md` holds only ids, types, tasks, size buckets and numbers, and only a full run with `MEASURE_PUBLISH=1` writes it; every other run writes `<run-dir>/results.md`.
- **Runs.** Every session uses `--setting-sources project --no-session-persistence`, the default model (`MEASURE_MODEL` pins one), `ENABLE_CLAUDEAI_MCP_SERVERS=false`, and one empty temp cwd outside `$HOME`. Connectors otherwise load into some sessions and not others, which made the probe's fixed cost 3.4k instead of about 0.7k tokens. From a cwd under `$HOME`, Claude Code loads `$HOME/.claude/CLAUDE.md` as an ancestor's project memory, about 8.5k tokens on every call. The plugin snapshots pin `MEASURE_LOCAL_MODEL` as the `model` option, and the report fails if any footer names another model. The order is one discarded warm-up per configuration, then 3 alternating no-file controls (`Reply with the single word OK.`), then one plugin-off and one plugin-on run per main file. Main-slot files below `MIN_DELEGATE_CHARS` (30k) use the low-floor plugin copy so the 20–30k bucket still measures delegation. The small files get 3 alternating reps against a plugin copy whose skill floor reads 1k instead of 30k (`lower_floor` in `measure/lib.sh` edits the sentences that name the 30k floor and the cap, and fails loudly if the skill is reworded); the real skill is never edited. Prompts (`measure/tasks.json`) never mention the tool.
- **Metric.** The gate is Claude cost, the cost-weighted usage that counts against a subscription: a job is its run's `total_cost_usd` minus the median control of its configuration, and the gate is 1 − Σ job cost on / Σ job cost off ≥ 50% over the main files. Fixed cost and break-even are computed on cost, with tokens beside them, and the small files take their median rep by cost. Beside the gate, not gated: T = input + cache_creation + cache_read + output (summed over the result event's `modelUsage`, minus the control's the same way), turns, the per-field split, timing and context growth. Context growth is the largest single-call input side in a run minus the control's: the file tokens that entered the main context. `.usage.iterations` holds only the last call, so the per-call figure comes from the assistant messages' input side, deduplicated by message id. Timing comes from every `code_task_files` footer, valid answer or not, with the session's duration when there is none; a file is SLOW when a call took over 60 s or a run timed out.
- **Status and the measured-run rule.** A run counts toward any metric only on positive evidence (`valid_run` in `measure/report.jq`, the one place every count, median, control, total and gate uses). All four usage counters and `total_cost_usd` are numbers, no trace line but the last failed to parse, the plugin tool is listed exactly when the configuration is on (controls included), and the status is `ok`. A plugin-on job's delegation failure also counts: `no-call` (no `code_task_files` call on the file) or `call-error` (every call errored, had no footer, read only some files, or carried a quality flag). Those stay in every total at their actual tokens and are never usable. Every other status leaves the metric it feeds `incomplete`, and an incomplete metric can never PASS. They are `no-server` (the tool is missing: a dead server measures nothing about delegation), `timeout`, `is-error` (an error result, checked before a missing result), `unknown` (no result event), `exit-N`, `facts-error` (the trace could not be scored: a bad line before the last, usage missing a counter, or a failed stage, which is named), `corpus-changed` (the file changed since the freeze, before or during the session), `snapshot-failed` (the graded copy could not be made), `base-no-read` (the baseline never read the file; a Read whose result is an error does not count, a Grep in content mode that matched does) and `plugin-leak` (the tool showed up in a plugin-off run). A job's cost also needs its configuration's 3 controls, and every gate needs a full corpus. A file's first job keeps a hash-verified copy in the run dir. The quality pass grades that copy, never the live file, and an answer without a matching copy is incomplete, not unusable.
- **Quality.** `measure/mechanical.jq` checks JSON answers (shape, label set, verbatim quotes after whitespace collapse) first; a failure skips the judge. Then `measure/judge.sh` runs one opus call per answer with tools off and `--json-schema`, and rejects a verdict whose `reference`, `invented` or `missed` is not an array. A failed judge call fails the pass. The judge sees the full file, the task and the answer, and never the configuration: the skill's attribution note (a line like `_Summarized by the local model._`) is dropped. Usable is recomputed as no invented claim and no missed reference point. The private `review.md` lists every unusable or FAILED answer plus two passes. The operator's `review-verdicts.tsv` (`<id>-<cfg>`, the answer hash `review.md` shows, `agree` or `disagree`, note; CRLF is fine) overrides those answers on `--report`, except that a FAILED job is never usable. A line that does not parse, or names an unknown answer, stops the report with its line number. Verdicts and operator lines bind to the answer they graded: a line for an answer that was since redone is ignored with a warning.

Knobs: `MEASURE_HOME`, `MEASURE_MODEL`, `MEASURE_LOCAL_MODEL` (`qwen3.6-35b-a3b-splash`; preflight tells an unreachable LM Studio apart from a model it does not list, and names the ids it does list), `MEASURE_RESELECT`, `MEASURE_ALLOW_SHORT`, `MEASURE_CONFIGS` (`off on`), `MEASURE_ONLY` (ids such as `f01`: a partial run, incomplete and private), `MEASURE_JUDGE_MODEL` (`opus`), and `MEASURE_JUDGE_JOBS` (4).

## Non-obvious design decisions

- **The launcher exists because houtini fails open, and it validates what houtini will use.** With `HOUTINI_LM_FILE_ROOTS` unset or empty, houtini's `code_task_files` reads any absolute path. Houtini also parses the variable as `split(/[:,]/).map(trim).filter(Boolean)` and `realpathSync`s each piece, so a string check in sh is not enough (`/repo:archive` adds a cwd-relative `archive`; `//` and `/tmp/..` resolve to `/`; a root ending in U+FEFF or NBSP is trimmed into a sibling). `scripts/resolve-roots.mjs` therefore runs in node with houtini's exact parse: it expands `$HOME`/`${HOME}`/`~`, refuses relative entries and any `:`, refuses any entry with leading or trailing whitespace (entries are never trimmed, so padding cannot silently name a sibling folder; Claude Code joins the option with a bare `,`), resolves with `realpathSync.native` (on-disk case, matching houtini's per-file realpath on case-insensitive APFS; houtini's own `realpathSync` returns that result unchanged), and refuses unless houtini's parse of the resolved path yields exactly that path. A resolved `/` is refused; a nonexistent folder (a configured folder missing on this machine) is skipped with a warning, and if every folder was skipped the launcher says none exist; any other resolution error (`EACCES`, `ENOTDIR`, `ELOOP`) or a non-directory exits 2. `launch-server.sh` exits 2 before starting houtini when no folder remains, and logs the resolved roots on stderr. The launcher also requires `node` and `npx`, and `cd`s to the plugin root (`CDPATH` cleared) before resolving and exec'ing. The root's `package.json` pins npm's project root there, so a stray `node_modules` in an ancestor directory cannot win either. Why: Claude Code spawns the server with the session's project dir as cwd, and `npx` runs a matching `@houtini/lm` found in `node_modules` up the cwd's ancestry (and reads a project `.npmrc`), so a repo carrying one would execute its code. Never launch houtini from `.mcp.json` directly.
- **Houtini's other environment variables are scrubbed.** The launcher unsets every `process.env.*` variable houtini 3.3.4 reads (`LM_STUDIO_*`, `OPENROUTER_API_KEY`, `HOUTINI_LM_STRUCTURED`, ...) before exporting the ones it sets, so ambient values cannot change routing or credentials. `tests/test-fence.sh` reads the list from the launcher, checks the environment a stub `npx` receives, and (when a cached 3.3.4 dist exists) fails if the dist reads a variable that is neither scrubbed nor exported; re-derive the list from the dist when bumping the pin.
- **`allowed_dirs` is a `directory` option with `multiple: true`.** Claude Code joins the array with `,` on `${user_config.allowed_dirs}` substitution, which is one of the separators houtini splits on (`:` or `,`). Consequence: folder names cannot contain `,` or `:`. It is `required` with no default: the folders a user reads are theirs to choose, and a default would name one person's layout. With the option unset, Claude Code never starts either server (its log says `Plugin option "allowed_dirs" isn't set`, probed with `claude -p --plugin-dir` and `--debug-file` against a copy with no default), so the launchers' empty-folders refusal is reached only through an empty saved value or a direct run; it names `claude plugin configure local-llm@ai-plugin-marketplace` (marketplace install) and, on its own line, `claude --plugin-dir <clone> plugin configure local-llm@inline` (labeled `--plugin-dir checkout`), both with `--values-stdin`, plus `/plugin` and a restart. A value saved by the user reaches the launcher literally (`$HOME/...` included), and a harness that must run headless without saving one (`tests/test-delegation.sh`, `measure/run.sh`) sets `allowed_dirs.default` in its own plugin copy; the resolver expands a leading `$HOME`, `${HOME}` or `~` (Claude Code itself expands only `${HOME}`). The value travels in `LOCAL_LLM_ALLOWED_DIRS`, not argv, so an empty value cannot vanish as an argument.
- **The endpoint must be loopback.** Both launchers accept only `http(s)://` URLs whose host is `127.0.0.1`, `localhost` or `[::1]` with an optional numeric port (no userinfo), so a misconfigured `endpoint_url` cannot send file contents to a remote server. The check is one string regex in `scripts/loopback.mjs`, deliberately not the URL parser, which would accept and normalize `127.1` or `0x7f000001`; the verify server runs it again in code and refuses to follow redirects, since fetch would re-send the request body (file text) to the redirect target. Houtini 3.3.4 sets no redirect policy, so its fetch follows them; that trusts whatever answers on the configured loopback port. Both launchers also source `scripts/no-proxy.sh`: Node's fetch sends requests through `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` when `NODE_USE_ENV_PROXY=1` or `--use-env-proxy` is set, so it unsets those variables (either case) and `NODE_USE_ENV_PROXY`; with no proxy defined, a flag that turns the env proxy back on has nothing to send through. The verify server also fails closed on its own: started directly with any of those seven variables defined, even empty, it refuses to start. It never consults `NO_PROXY`, because Node reads `no_proxy ?? NO_PROXY` (an empty lowercase value beats `NO_PROXY='*'`) and every exemption rule tried here missed a case. The check covers the inference endpoint only; see the next bullet.
- **Accepted risk: houtini's Hugging Face metadata lookup.** At startup, and again every 7 days per cached model, houtini 3.3.4 sends the loaded model's id (never file text) to `huggingface.co/api/models/...` to fetch model metadata (`dist/model-cache.js`). No setting in 3.3.4 disables it, and the loopback check does not cover it. So the accurate claim is narrower than "nothing leaves the machine": the plugin never sends file text to a remote model server. What Claude itself receives (the local model's answer, any spot-check lines, a fallback read) goes to Anthropic like any other Claude Code context.
- **Fence semantics are houtini's.** Roots and files are `realpath`ed before comparison, so symlinks out of a root and sibling-prefix directories (`root-evil` next to `root`) are rejected; the rejection never echoes file contents.
- **`HOUTINI_LM_API_KEY=not-needed`.** LM Studio needs no key; setting a dummy stops houtini from falling back to `OPENROUTER_API_KEY` from the user's environment.
- **`HOUTINI_LM_STRUCTURED` stays unset.** Plain text output is the contract.
- **`HOUTINI_LM_MAX_FILE_MB=1`** (houtini's minimum) caps a single read at 1,000,000 bytes; the context cap is clamped to 1,000,000 chars too.
- **`npx -y @houtini/lm@3.3.4` with `npm_config_prefer_offline=true`.** The exact pin fixes houtini's own code (the fence code stays reviewed) but not its dependencies: 3.3.4 ships no `npm-shrinkwrap.json` (npx ignores a package-lock), and its one direct dependency is a range, `@modelcontextprotocol/sdk ^1.26.0`, so the first install resolves whatever matches then and the npx cache freezes that resolution until cleared. That residual supply-chain exposure is accepted; re-check it with `npm view @houtini/lm@<pin> dependencies` when bumping the pin. The offline preference makes startup hit the npx cache (about 0.4 s warm) instead of the registry. Never pin below 3.3.3: 3.3.0–3.3.2 hid answers from Claude Code. Re-run `tests/test-fence.sh` when bumping the pin. The first launch on a cold npx cache needs network and can take a few seconds; if the server times out, reconnect via `/mcp`. Because the launcher unsets the proxy variables before `exec npx` (an env proxy would also carry houtini's loopback inference, file text included), that first fetch cannot use a corporate proxy: pre-warm the cache once from a shell that still has the proxy set, outside any project with a `node_modules`, with `npx -y @houtini/lm@3.3.4 </dev/null` (the server starts, sees stdin closed and exits 0), and `prefer_offline` uses the cache from then on. The launcher exits 2 with a clear message when `npx` is missing.
- **Oversized input is a hard error, not a truncated summary.** The limit is the loaded model's context window in tokens, not houtini's byte cap. The size hint estimates a cap from the loaded context, reserving prompt and answer room; text that still exceeds the context returns `Error: Upstream model error mid-stream: ... context_length_exceeded` and no summary. Houtini does not truncate silently. Use the size hint before delegating, or `wc -c` only when no hint supplies the size, because the error costs a round trip and real prose tokenizes at a different rate.
- **The skill's thresholds are rules of thumb; its table is the swap seam.** `skills/delegate-local/SKILL.md` delegates unprompted only for the task kinds named by the size hint, from about 30k characters through the loaded-context cap (about 45k without a hint). `delegate_tasks` defaults to empty: real-file delegated answers were usable 4/10 vs 8/10 when Claude read the file itself, and cost 3% more. Opt in by saving `{"delegate_tasks":"classify,extract"}` through `claude --plugin-dir <worktree> plugin configure local-llm@inline --values-stdin` (restart Claude Code). Existing saved values still take precedence; save an empty string to turn them off. With no hint naming kinds, delegate only when the user explicitly asks for the local model ("use the local model to …"). Bulk checkable jobs over multiple files invoke `local-llm:batch-local` only on an explicit local-model or batch/local request; ordinary requests and single-file jobs never start batch. `scripts/context-cap.mjs` GETs `/api/v0/models` once per eligible prompt with a 1 s timeout, using the loopback check and refusing redirects. It uses the minimum loaded context across chat models, or the loaded model pinned by the plugin's `model` option. A missing or unloaded pin has source `pinned model not loaded`. Other unavailable or invalid metadata has source `fallback`; both assume 32768 tokens and carry a short reason (timeout, HTTP status, not loopback, no metadata, oversized metadata, or invalid context). The cap is `floor((contextTokens - 4096) * 1.6)`, clamped between zero and 1,000,000: 45,875 chars at 32768 tokens, 98,304 at 65536. Measured chars/token are 1.74 for gen_log and 2.4 for LM Studio logs; pure numeric CSV is about 1.0 and can still overflow, failing loudly with `context_length_exceeded` so Claude reads the file itself. Bytes are a char proxy, not a token guarantee. Claude reuses the size hint without another `wc -c`; only unhinted files need that size check. The skill and deferred tool schema load in the same assistant message because they are independent. For a classification, or a summary enabled by the hint, no spot-check is needed when no single fact is load-bearing; when a specific fact, number or name matters to the user's question, use one targeted Grep (a few lines). Footer completeness, rejection of empty/error/flagged answers, JSON parsing for extraction and local-model attribution still apply; a quality flag or partial read requires reading the file yourself. Every houtini-specific name in the skill (tool, schema lookup query, footer field, error and quality-flag string, the `allowed-tools` line) sits in the skill's one table, taken from houtini 3.3.4's dist; swapping the server edits that table and the frontmatter, `.mcp.json`'s launcher, the size hint's schema lookup query, and `measure/footer.jq` (the measurement's only footer parser), and nothing else. The skill loads into every session, so it stays under 80 lines (`test-fence.sh` checks). Known limits of the cap, both loud: it reserves 4096 tokens, while houtini asks for up to a quarter of the context for its answer, so a long extraction on a file near the cap can stop with `Quality: hit-max-tokens` (the skill then discards it); and the batch default window assumes 1.6 chars/token, while numbered dense logs measure about 1.5, so a full window can end `finish_length`. Set `max_window_chars` lower for such jobs.
- **Permissions (headless `claude -p`, no `--allowedTools`).** A skill's `allowed-tools` pre-approves the MCP tool for the turn that invokes it (negative control: the same skill without the line has `code_task_files` denied). It cannot approve the `Skill` call that loads it: without a rule that call is denied and the model falls back to calling the tool, which is also denied. A plugin cannot ship allow rules in `settings.json` (only `agent` and `subagentStatusLine` take effect), so `hooks/hooks.json` ships a `PreToolUse` hook (`scripts/approve-own-tools.mjs`) that allows `local-llm:delegate-local`, `local-llm:batch-local`, the exact read-only tools `mcp__plugin_local-llm_local-llm__code_task_files` and `mcp__plugin_local-llm_local-verify__verify_claims`, and a whole Bash command `node "<resolved plugin root>/batch/run.mjs" <args>`. Optional quoting, a final `&`, and Bash's `run_in_background` input are supported. The hook lexes the entire command: shell operators, glob/brace expansion, substitutions, backticks, newlines and redirections outside literal quoted arguments get no approval; double quotes cannot contain expansion. Only exact absolute script paths whose realpath is unchanged are allowed, rejecting `..` and symlinks out. Batch approval also resolves `CLAUDE_PLUGIN_OPTION_ALLOWED_DIRS` (when set; unset or empty approves nothing, since there is no manifest default) through `scripts/resolve-roots.mjs` and realpaths every input into those roots. Only `--job-json <inline>` (required) and `--number` are approved. `--job`, `--out`, `--transcripts` and the manual flattener CLI are never approved. There is no trusted staging directory. Approved runs write only to a fresh private directory from `mkdtemp` under the OS tmpdir, creating output files exclusively (`wx`) and appending through their open descriptors, plus the band lane file `$HOME/catalyst/band/lanes/local-<pid>.json` (see Batch runner), whose tmp file is created exclusively, so a planted symlink fails that run open and is unlinked, never followed. Bash input with `dangerouslyDisableSandbox` set, or without an absolute `cwd`, gets no approval. Bash commands do not receive the plugin's `endpoint_url`/`model` options, so the runner uses `LOCAL_LLM_ENDPOINT_URL` or the default endpoint; a non-default setup exports that variable. A command that fails any other check (the lexer, the flags, the `--job-json`/`--number`/`--transcripts` rules, a missing input, an input outside the roots, when the roots resolve) gets no hook output, leaving the normal permission flow to decide, never a deny. Only a command that passes all of those and is withheld because `allowed_dirs` is unset, will not resolve (a refused or missing folder, a non-zero exit, or no folder at all; the reason points to the README's "Choose the folders the local model may read"), or times out resolving prints exactly one JSON line, `{"systemMessage":"local-llm: batch auto-approval skipped: <reason>"}` (a fixed reason, never a path), with no `hookSpecificOutput`: Claude Code shows it to the user as `PreToolUse:Bash says: ...` (checked with a headless `claude -p` run) and the normal permission flow still decides. The hook never denies, and stderr from an exit-0 hook is never shown, so it carries nothing. Commands that are not the runner print nothing. It does not grant general Bash or Write access. The matcher includes Skill, Bash, Read and the two tools; every other houtini tool (`chat`, `custom_prompt`, `embed`, ...) stays unapproved, and near-miss names (another plugin's or server's prefix, a suffix, other case) stay silent. Both tools are safe to approve because their launchers fence them to the allowed folders (the verify server re-checks the fence, loopback and the proxy environment itself), they only read, and inference stays on loopback. Its name matters because asking plainly ("use the local model to ...") can make Claude load `code_task_files` through ToolSearch without the skill, and `allowed-tools` only applies once the skill is loaded. The hook requires the contiguous runner path in the raw command text, so the README's path-anchored rule `Bash(*batch/run.mjs*)` covers every form it approves (a rule that begins with `node` or with the exact path would miss quoted forms). A deny rule on the tool name still wins over the hook: the hooks reference says so, and live runs confirmed it: `--disallowedTools mcp__plugin_local-llm_local-llm__code_task_files` with case g's prompt, and a settings-file `permissions.deny` entry on each of `code_task_files` and `verify_claims` with the plugin hook active, each left the tool out of Claude's pool (ToolSearch found no match) and Claude fell back to Read. Claude Code's `Read(...)` deny rules apply to built-in tools only, not to MCP tool arguments, so they do not constrain `code_task_files` or `verify_claims`: `allowed_dirs` is the only boundary on what the local model reads, and the docs say so rather than implying a folder deny protects it. A `UserPromptSubmit` hook (`scripts/size-hint.mjs`) stats the path-like tokens in the prompt (absolute, `~/`, or relative to the hook input's `cwd`; at most 100 stat calls) and, for up to three regular files of at least 30,000 bytes, queries context metadata once and emits the delegation instruction only through the cap. Its line states the size in bytes (a char proxy), context tokens, cap chars and source, then instructs Claude, for exactly the known read-only kinds in `delegate_tasks` (default empty: no delegation instruction), to invoke `local-llm:delegate-local` with Skill and ToolSearch query `select:mcp__plugin_local-llm_local-llm__code_task_files` in the same assistant message before reading the file, including the user's own project files. It explicitly says to reuse the stated size without running `wc -c` again. Above the cap it says the file is too big for the loaded model's context: `Grep or Read the relevant slices. Only when the user explicitly requests a local batch over multiple files, use batch/run.mjs.`. Multiple hinted files whose summed size exceeds the cap get one call per file. A fallback is labeled `assumed 32k context (model metadata unavailable: <reason>)`. Claude Code exports plugin options to hooks as `CLAUDE_PLUGIN_OPTION_*` only once saved; manifest defaults are not exported, so until then the hook falls back to the default endpoint (or an explicit `LOCAL_LLM_ENDPOINT_URL`) and reads the `delegate_tasks` default from `.claude-plugin/plugin.json`. The saved `CLAUDE_PLUGIN_OPTION_DELEGATE_TASKS` takes precedence even when empty. Its comma-separated known kinds are `classify`, `extract`, `summarize`, `draft`; whitespace is trimmed, duplicates removed, and unknown kinds ignored with a stderr note. Empty or all-unknown values emit no delegation instruction, but retain the too-big note. Add `summarize` only for a local model whose summaries have been measured as reliable. The real-file result (4/10 usable delegated vs 8/10 direct, at 3% more cost) motivates the empty default. Smaller files produce no hint or API request. The hook never reads file contents; its bounded lookup falls back when LM Studio is down, within the 5 s hook timeout. `wc -c` and other read-only shell commands are auto-allowed, but compound or piped shell commands are not, so the skill sends Claude to the Read and Grep tools. Do not run the harness with `disableAllHooks`, which disables that hook; `--setting-sources project` keeps user hooks out instead.
- **local-verify is our own server, in node with no dependencies.** houtini has no claim-checking tool, and a hand-rolled stdio MCP server (newline-delimited JSON-RPC: `initialize`, `ping`, `tools/list`, `tools/call`; notifications ignored) is one short file, which beats a supply chain. `initialize` echoes the client's protocol version when it is one of 2024-11-05 through 2025-11-25, else answers the newest (Claude Code 2.1.302 asks for 2025-11-25). `notifications/cancelled` aborts that call through its signal, so its queued and in-flight requests stop and free their slots, and its reply is suppressed as the spec asks (Claude Code's bundled MCP client sends it when it abandons a request). When the client closes stdin the server aborts every running call and exits 0, and a closed stdout (EPIPE) exits quietly instead of crashing. Every request field is type-checked before use and both sync and async handlers are wrapped, so a malformed request gets a JSON-RPC error and the server keeps running; exceptions go to stderr with their stack (the MCP log), never stdout. `launch-verify.sh` runs the same resolver and loopback check as houtini's launcher and passes the resolved roots in `LOCAL_VERIFY_ROOTS`; the server refuses to start without valid roots or with a remote endpoint even when run directly. File reads follow houtini's fence (realpath the file, then equal to a root or under `root + sep`; a refusal names the allowed folders, which are config, and where a symlink or `..` path resolves), then go through one descriptor: open with `O_NOFOLLOW | O_NONBLOCK`, fstat it for type and size, read at most 1 MB + 1 byte from it. An ancestor directory swapped between the realpath and the open is a declined risk: exploiting it needs a process that can already write the allowed folders, which could read the files directly. Empty files and files that are not valid UTF-8 are refused, and the files together are capped at 1 MB; practical input size follows the size hint's loaded context cap (about 45k chars at a 32k context, with less room for claims and samples; `wc -c` is a char proxy), since the model's context runs out first and returns the `context_length_exceeded` diagnostic. Any unreadable path fails the whole call, because judging claims against part of the source would read as NOT_SUPPORTED. Errors name the path and reason, never file text, and logs follow one rule (`server/errors.mjs`): only messages this server wrote (`VerifyError`) and allowlisted metadata (`name`, `code`, `errno`, `syscall`, `status`, our own stack frames) are ever printed, never a raw error object or a foreign cause, because undici's `HTTPParserError.data` keeps raw response bytes, which can echo the prompt. In replies, an upstream error becomes a fixed diagnostic from the HTTP status and an allowlisted error code, read only from structured fields (`error.code`, `error.type`), since free message text can echo the prompt; an identifier-shaped code outside the allowlist is logged to stderr, never replied. LM Studio wraps engine errors as a string, `Engine protocol predict request returned 400: {...}` (a context overflow carries `code: context_length_exceeded`), and reports nothing loaded as `No models loaded. ...`; those two forms are matched by their anchored prefix and then read structurally. Several bad paths are all listed with their causes, and sizes near the cap print in bytes.
- **verify_claims is the spike's method, and its output is a hint.** Each claim gets k samples (default 10) at temperature 1.0 with `reasoning_effort: "none"`, each with the spike's three options (SUPPORTED, CONTRADICTED, NOT_IN_SOURCE) in a seeded shuffled order and the answer forced to that enum by JSON schema; the votes collapse to SUPPORTED vs NOT_SUPPORTED (a tie is NOT_SUPPORTED), which is the form that scored 48/48 with no false accepts in the spike. `p_supported` is the SUPPORTED vote share and `agreement` the share that agrees with the label. The model is the pinned `model` option, else the chat model `/api/v0/models` reports loaded, else (a server without that API) the only non-embedding model `/v1/models` lists; when the load state cannot be known, or several chat models are loaded, it says so and asks for the model option instead of naming a model LM Studio might load, and when only embeddings models are loaded it says no chat model is loaded. The caller declares `kind`: a claim is `{text, kind: "lookup"}` only when it is a plain fact checkable by finding one passage (no counts, order, comparisons, dates or quantifiers), and a bare string is `computed`. A regex classifier was tried first and dropped: each review round found claims it misfiled, and the caller, who wrote the claim, knows what checking it takes. The spike's confident errors (7 unanimous wrong of 48) were all computed claims. Every result carries `auto_accept: false`, always; the result is a hint.
- **verify_claims bounds its time.** Requests from every call share 4 slots (LM Studio's default parallelism for one model). Each request times out after 45 s and is retried once with the same body (the spike saw a single request hang); a sample whose answer is cut off (the schema allows leading whitespace, and a temperature-1 sample can spend all 100 tokens on newlines) is redrawn once with another seed, and two such draws fail the claim with a diagnostic (finish_reason, and whether the content was empty, non-JSON or off-enum). Nothing else is retried. A call stops at a 240 s budget, and a request still queued for a slot leaves the queue when its call's budget runs out. A failed sample stops its claim's other samples. A claim that cannot finish (budget, two timeouts, a failed request) comes back `NOT_RUN` with a reason beside the claims that did (each claim's own failure logged to stderr with its stack; a budget overrun or cancel is logged once for the call), with `partial: true` and an `error`; the call fails outright only when no claim finished. Budget and timeout errors say "send fewer claims or a smaller k". `LOCAL_VERIFY_REQUEST_TIMEOUT_MS` and `LOCAL_VERIFY_BUDGET_MS` override the two times (positive integers, else the server refuses to start); the tests use them.
- **Tool names** for a plugin server are `mcp__plugin_<plugin>_<server>__<tool>`: houtini's are `mcp__plugin_local-llm_local-llm__<tool>` (`code_task_files`, `discover`, ...) and the verifier is `mcp__plugin_local-llm_local-verify__verify_claims`. Use the full name in `allowed-tools` and permission rules.

## Batch runner

`skills/batch-local/SKILL.md` (at most 50 lines) triggers only when the user explicitly asks for the local model or a batch/local run over many files (e.g. "use the local model to classify these 200 tickets" or "run a local batch over these transcripts"). Ordinary requests never trigger it; single-file jobs, judgment, synthesis and writing never use batch. Paid 60-ticket runs started the runner unprompted but took 14–17 Claude turns and $0.19–0.44: inline-JSON quoting hit Claude Code's brace-expansion check, globs were rejected, and checking rows led Claude to re-read tickets. See `docs/results.md`, section D.

While it runs, `batch/lane.mjs` writes `$HOME/catalyst/band/lanes/local-<pid>.json` (Catalyst's lane-file format) so the runner shows in Catalyst's band when Catalyst is installed (it creates `band/lanes/` inside an existing `$HOME/catalyst` and never creates `$HOME/catalyst` itself); the file is removed on exit, SIGINT and SIGTERM, and a failed write prints one stderr line (`local-llm: could not write a lane file in <dir> (<code>); running without a band lane`) and the run goes on unchanged (the line ends `; cleanup failed (<code>)` when removing the leftover tmp file failed too); without `$HOME/catalyst` it is silent. The label is `LOCAL_LLM_MODEL`, else the model the context-cap query names (only when exactly one chat model is loaded, or the pinned one), else `local`: so it is `local` when the job sets `max_window_chars` (no query is made), when several models are loaded, or when the query fails, unless `LOCAL_LLM_MODEL` is set. `CATALYST_TASK` sets the task.

For interactive sessions, write the job JSON to a scratch file with Write, resolve `<base directory>/../../batch/run.mjs` from the skill's displayed base directory, and start one Bash command with `run_in_background: true`. Expand globs yourself from a listing (e.g. `ls`) and pass explicit file paths. Each job asks for one kind of fact with a strict row schema containing `line`, `quote` and the fact fields, and `check: "quote-in-line"`. Interpretation-heavy kinds use about 20k-char windows. Wait, read the returned `index.md`, and check only rows the user's answer depends on. Do not re-read inputs to check rows: that defeats the batch. Report counts, no-row windows and failures. Quote validation proves location, not semantic correctness or complete recall.

```bash
node "<resolved plugin root>/batch/run.mjs" --job "<scratch job.json>" --number "<input 1>" "<input 2>"
```

The runner uses node stdlib and Bash's filesystem access. `--job` and Write use normal permissions. For headless use, replace `--job <file>` with `--job-json '<job JSON>'`: the hook auto-approves eligible whole runner commands, realpathing inputs into `allowed_dirs`. `--transcripts` runs are not auto-approved (transcripts hold copies of files from every past session), so they prompt. The hook also approves Reads of the runner's four output files in its own mode-0700 `mkdtemp` dir (`local-llm-batch-XXXXXX` directly under the OS tmpdir, user-owned, no symlinks or hardlinks); this assumes the hook and Bash share `TMPDIR`, and fails to a prompt otherwise. Unquoted shell words are limited to an allowlist (letters, digits, `._/,:@%+-`), so expansions such as zsh's `=cmd` never pass. Known limit: the hook realpaths each input once, but the runner opens each input only when it reaches it, so the window between check and open lasts the whole run, not an instant, and a concurrent writer inside the allowed folders could swap a file for a symlink during it; that needs a process that can already write there, which could read those files directly.

Use `--transcripts` instead of `--number` for Claude Code session JSONL; the flags are mutually exclusive. The runner calls the exported `flatten` function in memory before windowing. Flattened lines are `L<n>\t<role>\t<kind>\t<text>`, one per block, with newlines folded and blocks cut at 2000 characters. Thinking and non-message entries are skipped; `queued_command` attachments become user text lines. Per-file stderr and the index report flattened line counts and unparseable input lines skipped. Raw text uses `--number`, which adds `L<n>\t` in memory while preserving physical line numbers, including blank lines. Sources remain unchanged. Already numbered inputs need neither flag.

Each approved run uses a fresh private directory under the OS tmpdir; the final stdout line is its absolute `index.md` path, including failed/aborted runs that produced an index. Files are created exclusively (`wx`); JSONL output is appended through the descriptors opened at creation. The interactive recipe uses `--job <file>` instead of the headless `--job-json`; the CLI also accepts `--out <dir>` (existing output files are refused rather than overwritten). Neither `--job` nor `--out` receives automatic approval. The manual `node batch/flatten-transcripts.mjs <out_dir> <session.jsonl>...` CLI also remains available through normal permissions.

A job is `{"prompt", "row_schema", "check": "quote-in-line" | "none", "max_window_chars"?, "reasoning_effort"?, "min_rows_per_window"?}`. `min_rows_per_window` is an optional positive integer (off by default; a bad value exits 2). It counts returned rows before the check; a short reply records `under_min_rows` with detail `<n> rows` and still writes the rows it got. When `max_window_chars` is omitted, it uses `scripts/context-cap.mjs`'s shared formula with a reserve of `MAX_TOKENS` (4000) plus 1024 prompt/wrapper tokens: `floor((contextTokens - 5024) * 1.6)`, clamped between zero and 1,000,000 (44,390 chars at 32k, 96,819 at 64k). A context leaving no window room is refused with advice to load a larger context or set `max_window_chars`. The index header states the cap and source (`loaded`, `fallback`, `pinned model not loaded`, or `job` for an explicit cap), including the reason and 32k assumption for a fallback. Each input is split into windows of whole lines; each window is one temperature-0 chat call with a strict `json_schema` reply of `{rows: [row_schema]}` and `reasoning_effort` `none` unless the job sets it: with reasoning on, the loaded Qwen spent all 4000 tokens thinking on 11 of 19 transcript windows and returned no rows. Rows get `file` and `window` (the runner's keys win; a `row_schema` declaring `file`, `window` or `reason` is refused at startup). With `quote-in-line` the input must be numbered lines (`L<n>\t...`), and a row must carry `line` (an id from the window) and a `quote` of at least 12 characters (or the whole text) that is a substring of that line's text, not of its id (or the role/kind metadata in flattened transcripts; exact, then whitespace-normalized); rows that fail go to `dropped.jsonl` with a reason. A progress line per window goes to stderr.

Outputs in the run directory: `rows.jsonl`, `dropped.jsonl`, `failures.jsonl`, and `index.md` (under 60 lines), the one file Claude reads, so it never claims more than happened. It is a `RUNNING since <time> (pid N)` stub from the start of a run until the final index is renamed into place, so a killed run reads as running, not as complete; a manual run refused at startup removes any previous `index.md` in its output directory. The header says `Completed: A of W windows answered`, adding `; Z returned no rows` for answered windows with an empty reply or all rows dropped by the check, and `; N under minimum rows` for replies below `min_rows_per_window`. The index gives the combined no-row count and up to 10 `(file, window)` ids, explicitly including all-dropped windows. The header ends `; N input problem(s) skipped.` when an input was unreadable, empty, over the cap or had duplicate line ids. Other headers are `ABORTED ...` or `FAILED: no window answered (last failure: ...)` (exit 1 for the last two); it also gives windows and files reached, kept and dropped rows, kept rows per `kind`, failures by type, wall time and token totals. Failure types: `line_over_cap`, `empty_input`, `unreadable_input`, `duplicate_line_id` (a window is not sent), `finish_length`, `malformed_reply` (after one retry), `under_min_rows` (an answered reply below the job minimum; detail `<n> rows`), and the request failures `endpoint_unreachable`, `timeout`, `http_error` (detail is the status and an allowlisted code such as `context_length_exceeded` or `no_models_loaded`, never body text) and `bad_envelope`. Three consecutive failed requests of any request type abort the run; only an answered window resets the count. Redirects are not followed.

The endpoint comes from `LOCAL_LLM_ENDPOINT_URL` (default `http://127.0.0.1:1234`) and must pass `scripts/loopback.mjs`; like the verify server, the runner refuses to start when a proxy variable or `NODE_USE_ENV_PROXY` is defined, and when two inputs share a basename (results are keyed by it). Windows run sequentially; `LOCAL_LLM_MODEL` pins both the context lookup and chat requests, otherwise the model is whatever LM Studio has loaded. Transcript text is private: never commit flattened files or rows.

## Unversioned

This plugin carries no `version` field in `.claude-plugin/plugin.json`. Claude Code keys an unversioned install by the git commit SHA of the source, so every merge to `main` is a release. `claude plugin validate .` warns "No version specified" for this; that one warning is expected and accepted. Don't add a `version` field to silence it.

## Don't edit the plugin cache

The installed copy lives under `~/.claude/plugins/cache/` and is overwritten on plugin update. Edit the source repo and reinstall. To try a change without installing, run `claude --plugin-dir <worktree>`.
